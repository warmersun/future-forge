# Hosted loose quest resolution

This is the server-side read contract for the split v2 release. The portal must configure `FF_QUESTS_BUCKET`, `FF_QUESTS_OBJECT_PREFIX` (optional), and `FF_PREDICTION_BANK_ROOT` (the approved HTTPS directory `https://warmersun.com/predictions/`). Missing or invalid bank configuration fails closed. No client URL is used.

A current private catalog card has `storage: "loose-v2"`, its usual access metadata, and `packageRef: { packageId: "loose-quest", questId: "<quest-id>", revision: "sha256:<64 lowercase hex>" }`. The catalog card's `id` must equal `questId`. The revision is SHA-256 over the exact UTF-8 quest JSON bytes. Those bytes must be retained at `<prefix>/loose-quests/<quest-id>/<64 lowercase hex>.json`; the path is derived, never taken from a card or client. The quest must include `predictionBankId` and `predictionBankRef: { id: "<bank-id>", sha256: "<64 lowercase hex>" }`, with matching IDs. Identifiers are lowercase slugs. The raw bank bytes are fetched only from `<configured-root>/<bank-id>/<sha256>.json`, redirects disabled, then hashed and validated with the quest and its grants. Old quest bytes therefore pin the exact old bank. Both revisioned quest and public bank objects must remain available for saved runs; missing or changed bytes fail closed. Public banks are not access-controlled; the portal checks current catalog membership and both current and saved quest access before returning a mission.

Existing package-shaped run references are used so official start and Continue can bind to retained revisions without a database schema change. A `loose-v2` catalog entry without a valid binding is not accepted. `scripts/publish-loose-quests.mjs` publishes projected quests and verifies public bank bytes and object/catalog readback. The tracked `deploy-quest.sh` prepares the split projection and publishes the public content first. The portal code and configuration must be deployed separately before the wrapper's readiness check will allow publication. Module-wrapper publication is not implemented and fails closed. The catalog writer is last-writer-wins, like the existing v1 writer; coordinate all catalog publications and do not run them concurrently. A transition from another package identity can make earlier saved runs unavailable. Actual Neon retention, public bank availability and authenticated end-to-end behavior require live verification.
